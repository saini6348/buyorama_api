Executive Summary

The application is composed of a Next.js frontend (admin SPA at /admin-backoffice) and a standalone NestJS/TypeORM backend (buyorama_backoffice) exposing CRUD endpoints under /api/.... The frontend and backend sit on separate ports and communicate over plain HTTP on localhost.

The most severe architectural defect is that the authentication token is purely a client-side UI gate and is never verified or enforced by the backend. Every /api endpoint — including create, update, delete, user management, and site settings — is reachable without authentication, authorization, or CSRF protection. Effectively the API is wide open to anyone who can reach it.

Notable positive: SQL access is performed through TypeORM's parameterized QueryBuilder/Repository APIs; no raw-SQL string-concatenation or SQL-injection sink was found. The ISR revalidation route is correctly protected by a secret.

Findings are listed by severity with description, impact, reproduction steps, recommended fixes, and code location. No code changes were made, preserving existing functionality and APIs.

Scope & Methodology

Reviewed components:

  • Authentication & authorization (JWT issuance, guards, role handling)
  • User management APIs (/api/users/*)
  • Content / brand / coupon / card / settings CRUD APIs
  • Data validation / DTOs / mass assignment
  • SQL build paths (TypeORM QueryBuilder & Repository) for injection
  • Frontend XSS sinks (RichTextEditor, dangerouslySetInnerHTML)
  • File-upload handling, session/token storage, CORS, rate limiting, secret handling

Methodology: static analysis of application source, authentication-flow tracing, and endpoint-by-endpoint authorization / validation control review. Prioritization follows the OWASP Top 10 and OWASP API Security Top 10.

Critical Findings

CRITICALFinding C-01 · CWE-287 / CWE-639

Broken Authentication & Broken Object Level Authorization — entire API is unprotected

Description

No route guard, JWT strategy, role guard, or useGlobalGuards is attached to any controller or endpoint. The JWT signed at login is returned to the browser, stored in localStorage, and used only client-side to decide whether to render admin pages. Subsequent API calls do not send the token, and the server never validates it. All /api routes (list/create/update/delete/status, user creation, settings update) are anonymous.

Impact

Complete compromise. An unauthenticated attacker can enumerate, create, modify, and delete all brands, coupons, cards, content, feeds, user accounts, and site settings. They can create admin/editor accounts, list all user records, reset passwords, and deface or poison the entire public catalog (affiliate footprint, SEO, pricing). Because the API is reachable independently of the SPA login page, the login screen provides no real protection.

Reproduction Steps
  1. Do not authenticate at all.
  2. Send POST /api/users/create with any name/email/password → 201 Created, no auth required.
  3. Send POST /api/users/list with no token → returns all user records.
  4. Send POST /api/settings/update → rewrite public site settings.
  5. Send POST /api/coupons/delete, /api/brands/update, etc. → mutate data without authenticating.
Code Location
buyorama_backoffice/src/main.ts                    (app.enableCors(); — no guards registered)
buyorama_backoffice/src/users/auth.service.ts     (token generation; no validation/guard)
buyorama_backoffice/src/users/users.controller.ts  (no @UseGuards)
buyorama_backoffice/src/brands/brands.controller.ts
buyorama_backoffice/src/content/content.controller.ts
buyorama_backoffice/src/settings/settings.controller.ts
buyorama_backoffice/src/coupons/coupons.controller.ts
buyorama_backoffice/src/cards-feeds/cards-feed.controller.ts
buyorama_backoffice/src/brand-feeds/brand-feeds.controller.ts
buyorama_backoffice/src/brand-coupons/brand-coupons.controller.ts
buyorama_backoffice/src/banks/banks.controller.ts
buyorama_backoffice/src/tags/tags.controller.ts
buyorama/src/lib/admin/http.ts                   (no Authorization header sent)
Recommended Fix
  • Register a global JWT auth guard and explicitly mark only public routes (e.g. POST /api/users/login).
  • Make the frontend send the token on every API request via Authorization: Bearer <jwt> or an httpOnly same-site cookie.
  • Add an RBAC model (roles/permissions) and enforce it server-side; only admins manage users, editors restricted to content.
  • Validate server-side that the authenticated identity/ownership matches the resource id being modified (closes IDOR).

High Findings

HIGHFinding H-01 · CWE-798

Hardcoded JWT Secret (predictable signing key → token forgery)

Description

The JWT module uses a default secret when none is configured:

JwtModule.register({
  secret: process.env.JWT_SECRET || 'your-secret-key',
  signOptions: { expiresIn: '7d' },
})

Tokens also expire after 7 days with no refresh/rotation logic.

Impact

If JWT_SECRET is absent, an attacker can forge valid JWTs for any user (including admins) using the well-known string your-secret-key, enabling trivial session impersonation once server-side validation is added.

Reproduction Steps
  1. Observe the fallback in users.module.ts.
  2. Sign a forged HS256 token with that secret and any sub/email.
  3. Present the forged token to impersonate the target user.
Code Location
buyorama_backoffice/src/users/users.module.ts
Recommended Fix
  • Require a strong, randomly generated JWT_SECRET from env and fail fast (throw) if missing rather than fall back to a default.
  • Prefer asymmetric signing (RS256) or short-lived access tokens + refresh rotation; keep secrets only in the environment.
HIGHFinding H-02 · CWE-79

Stored Cross-Site Scripting (XSS) via Rich Text Editor & Unvalidated HTML

Description

Rich text content is captured as raw inner HTML (document.execCommand + el.innerHTML) and re-injected with dangerouslySetInnerHTML in the admin editor. There is no sanitization anywhere in the pipeline (client or server), and the API endpoints accept arbitrary HTML strings for card/feed descriptions.

Impact

An attacker (or, due to C-01, any unauthorized party) can store a payload such as <img src=x onerror=alert(document.cookie)> or a javascript: link. It executes against any admin who opens the record for editing (rendered via dangerouslySetInnerHTML) and against any public surface rendering the field without escaping — enabling admin session hijack, data exfiltration, and site defacement.

Reproduction Steps
  1. POST /api/cards-feed/create (or brand-feed create) with description = <img src=x onerror=alert(document.domain)>.
  2. Open the Cards page and click Edit on that card.
  3. The editor's dangerouslySetInnerHTML executes the handler in the admin session.
Code Location
buyorama/src/app/admin-backoffice/cards/_components/RichTextEditor.tsx
buyorama/src/app/admin-backoffice/brand-feeds/[brandSlug]/_components/RichTextEditor.tsx
buyorama_backoffice/src/cards-feeds/cards-feed.service.ts   (stores raw HTML)
buyorama_backoffice/src/brand-feeds/brand-feeds.service.ts   (stores raw HTML)
Recommended Fix
  • Sanitize rich-text HTML server-side with an allow-list library (e.g. DOMPurify), stripping javascript: URLs, on* handlers, and tags such as script, iframe, object, embed, form, and style/event attributes.
  • Enforce a strict schema for link protocols (http:/https: only).
  • Prefer a schema-driven rich-text framework (TipTap/Slate) rather than raw contentEditable + innerHTML.
  • Use dangerouslySetInnerHTML only after sanitization and never trust stored values blindly.
HIGHFinding H-03 · CWE-269

Privilege Escalation / Mass Assignment on User Management

Description

POST /api/users/create, POST /api/users/update, and POST /api/users/update-status have no guard, so any caller may create arbitrary accounts, reset any user's password, and deactivate any user. DTOs have no role/scope constraints and the service derives no authorization from the session. If a role field is added later, a caller could elevate privileges by passing it in the body.

Impact

Total account takeover of all admin/editor accounts. An attacker can create a backdoor account, change any user's password to lock out staff, and pivot to full control of the platform's data.

Reproduction Steps
curl -X POST http://localhost:3011/api/users/update -H "Content-Type: application/json" \
  -d '{"id":"<admin-uuid>","password":"Mine1234"}'   # attacker now controls the admin account
Code Location
buyorama_backoffice/src/users/users.controller.ts
buyorama_backoffice/src/users/users.service.ts   (addUser, updateUser, updateStatus)
buyorama_backoffice/src/users/dto/create-user.dto.ts
Recommended Fix
  • Restrict user-management endpoints to authenticated users with an Admin role via a guard.
  • Never allow a caller to self-elevate; derive role from the authenticated session server-side, not the request body.
  • Use explicit allow-list DTOs with whitelisting and server-side authorization checks.
HIGHFinding H-04 · CWE-346

Cross-Origin Resource Sharing (CORS) fully open

Description

app.enableCors() is called with no configuration, which by default reflects any origin and permits any method. Combined with the absence of CSRF protection and lack of authentication, a malicious website can issue browser-based requests to the admin API on a victim's behalf.

Impact

Cross-origin data theft and cross-site request forgery become trivial. A victim visiting a malicious page can have their browser call the admin API to read or mutate data. Compounds the impact of C-01.

Reproduction Steps
curl -i -X OPTIONS http://localhost:3011/api/brands/list \
  -H "Origin: https://evil.example" -H "Access-Control-Request-Method: POST"
# If the response echoes evil.example -> vulnerable
Code Location
buyorama_backoffice/src/main.ts   (app.enableCors();)
Recommended Fix
  • Configure an explicit origin allow-list: app.enableCors({ origin:['https://buyorama.example'], credentials:true, methods:[...] }).
  • Add CSRF tokens (or require a custom header / SameSite cookies) for state-changing requests.

Medium Findings

MEDIUMFinding M-01 · CWE-312 / CWE-319

Sensitive Data Exposure — JWT in localStorage & plaintext HTTP

Description

The auth token and user object are persisted in localStorage (readable by any script in the origin, not server-invalidatable) and transmitted over plain HTTP on localhost.

Impact

Any XSS (H-02) or malicious browser extension can read localStorage and steal the token. Plain HTTP permits on-path interception. Token theft = session hijack.

Reproduction Steps
  1. Trigger stored XSS (H-02).
  2. Read localStorage.getItem('authToken') and exfiltrate it.
Code Location
buyorama/src/app/admin-backoffice/page.tsx   (localStorage.setItem("authToken"...))
buyorama/src/app/admin-backoffice/{dashboard,brands,content,coupons,cards,cardsSettings,brand-feeds}/page.tsx  (authToken reads)
Recommended Fix
  • Store the session in an httpOnly, Secure, SameSite cookie instead of JS-accessible storage.
  • Enforce HTTPS + HSTS in production.
  • Implement server-side revocation / short TTL + refresh rotation.
MEDIUMFinding M-02 · CWE-770 / CWE-20

Inconsistent / Missing Input Validation & Mass Assignment

Description

Only a subset of controllers (coupons, brand-coupons, brand-feeds, cards-feed) apply @UsePipes(ValidationPipe). Others (users, brands, content, settings, banks, tags) rely on services that spread DTOs with Object.assign or create({...}). Query params limit/offset/status are parsed ad hoc and not validated or bounded.

Impact

Unbounded limit/offset can be abused for resource exhaustion and over-enumeration; invalid types cause unexpected 500s (information disclosure); mass assignment lets callers set unintended entity fields (status, etc.), compromising data integrity.

Reproduction Steps
curl -X POST http://localhost:3011/api/brands/list -H "Content-Type: application/json" \
  -d '{"limit":999999999999,"offset":0}'        # resource exhaustion / huge payload
curl -X POST http://localhost:3011/api/brand-feeds/update -H "Content-Type: application/json" \
  -d '{"id":"x","title":"y","status":0}'         # Object.assign may set unintended fields
Code Location
buyorama_backoffice/src/coupons/coupons.service.ts            (Object.assign)
buyorama_backoffice/src/brand-coupons/brand-coupons.service.ts (Object.assign)
buyorama_backoffice/src/brand-feeds/brand-feeds.service.ts     (Object.assign)
buyorama_backoffice/src/cards-feeds/cards-feed.service.ts      (Object.assign)
buyorama_backoffice/src/users/users.controller.ts              (no ValidationPipe)
buyorama_backoffice/src/brands/brands.controller.ts            (no ValidationPipe)
buyorama_backoffice/src/content/content.controller.ts          (no DTO validation)
Recommended Fix
  • Apply a global ValidationPipe({ whitelist:true, transform:true }) to strip unknown fields and block mass assignment.
  • Add consistent DTOs with bounds (@IsInt/@Min/@Max) for limit/offset/status.
  • Replace Object.assign with explicit field-by-field assignment.
MEDIUMFinding M-03 · CWE-307 / CWE-770

No Rate Limiting / Brute-Force Protection on Login & CRUD

Description

No @nestjs/throttler, no IP-based limiting, no account lockout, and no anti-automation on the login or any CRUD endpoint.

Impact

Unlimited credential-stuffing / brute-force against the login form and unbounded automation of destructive CRUD (mass delete/spam), plus resource exhaustion at scale.

Reproduction Steps
  1. Loop thousands of POST /api/users/login attempts with varying passwords — no lockout or throttling is observed.
  2. Loop destructive delete/update-status calls at high volume — no rate limiting.
Code Location
buyorama_backoffice/src/users/users.controller.ts   (login)
buyorama_backoffice/src/users/users.service.ts      (login)
buyorama_backoffice/src/app.module.ts                (no ThrottlerModule)
Recommended Fix
  • Enable rate limiting (e.g. @nestjs/throttler) on login and all write endpoints.
  • Add account lockout / exponential backoff and optional CAPTCHA on login.

Low Findings & Defensive Notes

LOWFinding L-01 · CWE-693

Missing Security Headers / Error-Message Leakage

Description

NestJS app does not apply helmet, HSTS, X-Content-Type-Options, CSP, Referrer-Policy, or X-Frame-Options. Several services return verbose internal messages (e.g. 'Error fetching content: ' + error.message).

Impact

Clickjacking, MIME-sniffing, reduced XSS protection; verbose errors may leak stack/DB details to clients.

Code Location
buyorama_backoffice/src/main.ts
buyorama_backoffice/src/content/content.service.ts   (returns error.message to client)
Recommended Fix
  • Register helmet() and a strict CSP; add a global exception filter that logs details server-side and returns generic messages.
LOWFinding L-02 · CWE-434

File Upload Validation Is Client-Side Only

Description

The admin ImageUploadField enforces size (≤1MB) and image/* MIME-type and encodes as base64 data-URL. There is no server-side file validation (magic bytes, dimensions, storage policy); base64 data-URLs are stored in DB columns.

Impact

If rendered unescaped, increases the stored-XSS/DoS surface. Lower risk because data-URLs are embedded and displayed as images, but the server enforces no policy and DB columns could grow unbounded.

Code Location
buyorama/src/components/admin/ImageUploadField.tsx   (client-side validation only)
Recommended Fix
  • Move validation server-side (size, magic bytes, allowed extensions) and store files in a scoped object store instead of base64 text.
  • Serve uploads with no-sniff headers and never render via dangerouslySetInnerHTML.
LOWFinding L-03 · CWE-798

Secret Keys Committed / Defaults in Code

Description

The JWT_SECRET fallback 'your-secret-key' lives in source, a developer convenience that becomes a hazardous default if it reaches production. Admin quickstart docs also reference token-storage keys and a base-URL default for the admin API.

Impact

Reinforces H-01; if defaults ship to production, authentication can be completely subverted.

Code Location
buyorama_backoffice/src/users/users.module.ts
buyorama/src/lib/admin-api.ts   (ADMIN_API_BASE_URL default)
Recommended Fix
  • Load all secrets and service URLs exclusively from the environment; fail fast on missing values; never commit defaults.
  • Rotate any secrets that have appeared in source / documentation history.

Positive Security Notes

  • Parameterized queries: All data access uses TypeORM Repository / parameterized QueryBuilder; no raw SQL string concatenation or SQL-injection sink was identified.
  • ISR webhook protection: The Next.js /api/revalidate route validates a secret from environment and rejects unauthorized cache-busting.
  • bcrypt: User passwords are hashed with bcrypt rather than stored in plaintext.
